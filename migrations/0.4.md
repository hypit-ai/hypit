# Upgrade an existing project to Hypit 0.4

[简体中文](0.4.zh-CN.md)

Use this guide when moving a 0.3.1 project or framework integration to 0.4. Older projects should
first reach 0.3.1 with the [0.3](0.3.md) and [0.3.1](0.3.1.md) guides.

Hypit 0.4 has one current Author, Target-selection, Build and Result model. The release contains one
execution path. Migrate project sources and package code to the current interfaces, then remove any
local conversion script used for the move.

A conversion script may rewrite project files once, but it is not an Author Package, frontend,
Runtime adapter or permanent command. Its output must already be an ordinary current Source and
project resource; do not keep a compatibility object or alternate execution path after the move.

## Identify the affected boundary

| Project content | Review |
| --- | --- |
| `.svml`, `.svs` and assets | Preserve accepted media, update the locked installation, move durable material choices into Author Source, then check the real production |
| Project `packages/` or another Author Package | Migrate declarations, Manifest shapes, Producer results, Refinements, PreparedMedia inputs and Studio Companions |
| Model or Provider package | Keep the request contract Model-owned and migrate Endpoint capability and result interfaces |
| Custom Source frontend | Return the current source-neutral document shapes directly |
| Compiler, Runtime or Result integration | Migrate AuthorGraph, Target selection, Build Definition/Facts, ResultIntent and the current Result schema together |

Update the project dependencies and lockfile as one set. Rebuild project packages from their source;
do not treat an edited `dist/` or `node_modules/` file as the migration.

## 1. Preserve accepted work before upgrading

0.4 retains the project's public `@1` protocol identifiers but changes their current structures. Its
Result reader reads the current `hypit.build-result@1` schema only. Before changing the installation:

1. Record the executable and project paths with `hypit version` and `hypit paths`.
2. Keep the working 0.3.1 lockfile and installation recoverable during migration.
3. Use that installation to export every accepted Output that the project still needs:

   ```sh
   hypit get <build-id> --output <name> --to <project-path>
   ```

4. Keep the old Result directory as history rather than rewriting its manifests.

An exported image, video, audio file or evidence document becomes an ordinary project resource. Its
package-owned Author declaration gives it a Type and meaning in 0.4. The new production never needs
the old Build address in order to use that resource.

## 2. Move execution choices to their current owners

The Author Source owns the production and durable material references. Each command explicitly selects
the public Targets needed for that execution:

```sh
hypit check main.svml
hypit plan main.svml --target final.video
hypit build main.svml --target final.video --follow
```

Repeat `--target` to request multiple Outputs. If a project wants a shorter repeated command, use its
ordinary task runner or package script; do not introduce another Target document, default Target or registry.

An accepted generated file becomes ordinary project material and is referenced directly by its consumer:

```svml
<import as="asset" from="@hypit/media@1"/>
<import as="mediaop" from="@hypit/media-operations@1"/>

<asset:Video id="accepted-opening" src="./assets/opening.mp4"/>
<mediaop:Prepare id="opening-media" source={accepted-opening}
  video="primary-moving" audio="default" span-authority="video"/>
```

To ask for another generated take, Target `opening-generation.video`. That makes the generation branch
reachable; the generation package's retained declaration gives the completed material a cross-Build
lifetime. Adopting it remains a separate edit of the consumer reference.

## 3. Keep speech evidence explicit

Speech transcription and authored narrative alignment are separate operations:

```svml
<whisperx:Transcription id="opening-transcription"
  media={opening-media.media} language="en"/>
<speechalign:Alignment id="opening-alignment" narrative={story}
  segment={story.segment.opening} domain={opening-media.domain}
  evidence={opening-transcription.transcript}/>
```

`hypit transcribe` writes an editable `.transcript.svml` Source containing
`SpeechTranscriptEvidence`. Online transcription and imported evidence therefore enter alignment
through the same Type. The evidence file can be reviewed or corrected without changing authored
semantic intent.

## 4. Migrate Author Packages

### Declarations and values

Author packages compile syntax-neutral declarations. Their package compiler owns declaration
semantics; Frontends own text syntax. Values use one recursive `Value` model with `BlobRef` as a
reserved leaf. Replace `StoredValue` with `Value` and `blobRefObjectSchema()` with
`blobRefSchema()`.

`ValueSchema` describes accepted data, not Studio presentation. Put controls such as color pickers
on the package's Studio Companion.

### One result per Producer

A Producer declares exactly one result: a deterministic Output or an external Need.

```ts
const manifest = {
  format: "hypit.module@1",
  ...moduleRef,
  dependencies: [dependencyModule],
  types: ["Request", "Result"],
  capabilities: [],
  producers: [{
    name: "render",
    inputs: [{ name: "request", type: requestType }],
    result: { kind: "output", name: "result", type: resultType },
  }],
} satisfies ModuleManifest;
```

The handler returns either `{ kind: "output", value }` or `{ kind: "need", constraints }` according
to that declaration. Split an earlier multi-result operation into separate Producers connected by
explicit graph edges.

### Refinement

Structural Type validation belongs to the framework. A package Refinement is only the semantic
predicate owned by the exact Type:

```ts
createProducerPackageFacet(component.producers ?? [])
createRefinementPackageFacet(component.refinements ?? [])
```

Use `TypeRefinement`, `refinements`, `refineValue` and `refineRecord`. Concrete Needs appear only
after every Producer input exists; the plan itself already retains blocked Record dependencies.

### Prepared media and audiovisual structure

Visual and audio components accept `PreparedMedia` directly. Preparation preserves selected source
facts and its local TemporalMap; occurrence sampling composes with that map. Decoder working files,
CFR/PCM intermediates and caches remain private to the executing Provider.

Still pictures now carry the same explicit picture interpretation used by prepared video and
compositable surfaces. Add `picture="srgb"` to a `visual:Clip image={...}` or a still
`deck:Card source={...}`; do not add it to prepared timed media or surfaces. The Blob and extent do
not imply primaries, transfer, range, sample depth or alpha semantics.

Public delivery picture types are `OutputPictureSpec`, `VideoOutputPictureSpec` and
`FrameOutputPictureSpec`. `PictureObservation` records source tags and `PictureInterpretation` records
the interpretation selected during preparation. Prepare accepts `source` or `sdr-bt709`, and finished
video uses the BT.709 H.264 family.

Terminal visual structure is an ordered recursive `VisualScope` of Track, Stack and Process members;
each VisualTrack owns its ordered `present`, time-bounded `process` and `adjustment` items. Visual
z-order belongs to occurrences in their scope, not to reusable visual components. Transitions are
explicit relations over the exact intersection of two Clip Windows and lower to a time-bounded Track
Process. A `VisualTransitionEffect` is now the closed `VisualProcessEffect` with exact `outgoing` and
`incoming` ports; direct TypeScript effect constructors and stored values must carry `{ inputs, program }`
rather than a bare Visual Program.

For a sibling matte, declare an `@hypit/visual-matte` Effect and assemble it with
`<film:Process>` and exactly named `content` and `matte` Inputs. `channel="alpha|luminance"` and
`invert="true|false"` are explicit effect choices. Each Input is a recursive visual Scope; the Process
occupies one parent paint position and consumes its inputs instead of painting them again as siblings.
Do not encode this relation in Track ids or z-order. Audio remains an independently evaluated graph
and mixes into the Film's Audio Program.

`Composition` now owns its one Timeline. Do not pass a second `timeline` input to HTML, audio or
video compilation.

Frame-indexed spatial regions use `@hypit/spatial-sequence`. Keep the accepted sequence in an ordinary
SVML Source with an opaque `<sequence:Regions>` JSON body. Its `RegionSequenceDocument` declares one
exact Clock, frame count and normalized final-program region or `null` per Frame. In the main Source,
attach it with `<sequence:TimelineRegions document={...} timeline={...} canvas={...}/>`; Clock and
frame count must match exactly. Caption assigns meaning separately with an explicit
`<caption-fine:Follow role="..." series="..." missing="hide|authored-placement"/>`. Detection,
identity association, interpolation and correction happen before the author file enters the Build.

Use `FrameSpan` from `@hypit/timeline` for half-open frame intervals. `TemporalMap` endpoint identity
comes from its first target and final source domains; do not duplicate endpoint ids as metadata.

### Studio Companions

A Companion projects authored objects, timeline Items, preview hints and Inspector controls. It does
not create a second production model. Keep Item ids local to their Track and let Studio carry the
structured Track address. Recompile project packages after changing Companion code.

## 5. Migrate Model and Provider packages

A Model package owns its complete request Type, exact Capability, result Type, defaults and limits.
Generation does not impose a universal text/media/scalar port ontology or cross-model source limit.
Use `defineModelModule()` for a direct contract; the optional field-oriented helper is an
implementation choice rather than a protocol.

A Provider depends one way on the exact Capability it implements. Its Endpoint has one authoritative
`capabilities` list. Request support, scheduling and live pricing receive a concrete request only
after the Producer emits a Need. Immediate handlers and completed asynchronous operations return the
recursive `Value` directly.

## 6. Migrate frontends and execution integrations

Source frontends return their current document directly from `decode()` and use `SourceUnit` from
`@hypit/source`. Targets are public Output names and are represented as strings.

Framework integrations use these boundaries:

- `AuthorGraph` contains author Outputs with fixed Operation results and Operations.
- An author-facing target set resolves to `{ name, output, type }` entries for one finite execution.
- `BuildCompiler` combines the explicit Source and Target arguments with the same Author compilation;
  there is no separate Invocation package, preset document or compiler.
- Kernel persists an immutable `BuildDefinition` plus ordered `BuildFact[]`; `BuildView` is derived.
- Compiled Targets record the demanded execution goals independently from storage.
- `ResultIntent` names only reachable package-owned retained Outputs with their final Records.
- Result stores self-contained current values and files; it does not forward to another Build.
- An open Result draft is writable repository state, not a historical `BuildResult`. Only a finished
  Result has an outcome, finish time, execution log and external-operation evidence.
- Result has no editable or submission-time title. Source, Targets, Build id and retained Outputs are
  the recorded identity; subjective naming belongs in authored project material.
- Result operation evidence retains Provider acknowledgement/completion facts, receipts and explicit
  conclusions. Runtime ids, queue phases, progress, capacity pools and unacknowledged queued work do
  not become history.
- `hypit result export <build-id> --output <name> --to <path>` writes one retained Output; structured
  Types use the author exporter supplied by their owning package.

The Result manifest uses `sourcePath` for the recorded Author Source path. Plan JSON projects Targets,
external requests and diagnostics; it does not serialize Producer Step/Port/Record joins. Update the
current database and Result readers/writers together; do not add field aliases or shape-based detection.

## 7. Verify the migrated production

Run the framework and package checks that own the changed boundary, then verify a real project:

```sh
hypit check main.svml
hypit plan main.svml --target final.video
hypit studio --source main.svml --target final.video
```

Inspect generated media selection, Timeline extent, visual order, audio, Caption timing and final
rendering. Remove migration-only scripts after the project and its lockfile have moved to the current
interfaces.
