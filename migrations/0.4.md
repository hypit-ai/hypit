# Upgrade an existing project to 0.4

[简体中文](0.4.zh-CN.md)

Read this when moving a 0.3.1 project, Author Package, Provider, Runtime integration or Result
integration to 0.4. For an older project, apply the [0.3 project migration](0.3.md) and
[0.3.1 SDK migration](0.3.1.md) first.

0.4 changes the framework SDK and stored Result shape. It does not redefine a video's creative
intent. Ordinary `.svml`, `.svs` and `.svrun` projects that use released packages usually need only
a compatible dependency update, one `<value>` file adjustment if applicable, and verification.
Packages that construct graphs or integrate with Model, Endpoint, Runtime or Result APIs must migrate
the affected boundaries below.

## Decide which parts apply

| Project content | Required review |
| --- | --- |
| Sources, Recipes and Runs only | Preserve existing Results, update the locked installation, check `<value>` files, then verify the real production |
| Project `packages/` or another Author Package | Also migrate manifests, Producer results, Refinements and any Studio presentation hints |
| Model or Provider package | Also migrate the Model-owned request and the unified Endpoint capability declaration |
| Custom Source/Run Frontend | Also migrate the smaller Source and Run adapter return types |
| Custom compiler, Runtime or Result repository | Also migrate Author Graph, Build Definition/Facts and Publication Plan APIs |

Do not update only a global executable. The project lockfile and every directly selected package must
resolve to a compatible set. Use the package manager that already owns the project; Hypit has no
second package lock or automatic package upgrade mechanism.

## 1. Preserve accepted work before changing the installation

0.4 keeps public format identifiers at `@1`, but it intentionally does not guess the superseded 0.3
Result representation. A 0.4 repository reader therefore does not import old `result.json` files by
shape. Before updating:

1. Record the working executable and project locations with `hypit version` and `hypit paths`.
2. Keep the 0.3.1 lockfile and installation recoverable until migration is complete.
3. Export any accepted Outputs that must cross the upgrade while 0.3.1 can still read them:

   ```sh
   hypit get <build-id> --output <name> --to <path>
   ```

4. Preserve the original Result directory as history; do not rewrite its manifests by hand.

Exported media and value documents remain ordinary project inputs. Reference them explicitly from a
0.4 Run with `<file>` or `<value>`, or rebuild only when the user actually wants new work. A prior
0.3 Build id is not a valid 0.4 `<build-record>` source unless that Result was produced in the new
repository representation.

## 2. Update an ordinary video project

Update the project's existing Hypit dependencies and its lockfile together. Reinstall and rebuild
project packages; do not patch generated `dist` files or `node_modules` as the durable fix.

The official Run syntax still uses `<value>`, `<file>` and `<build-record>`. A JSON file referenced by
`<value from="...">` now contains the graph Value directly. Remove the old `StoredValue` wrapper:

```json
{ "kind": "inline", "value": { "enabled": true, "strength": 0.8 } }
```

becomes:

```json
{ "enabled": true, "strength": 0.8 }
```

Strings, numbers, booleans, null, arrays and objects follow the same rule. A Blob reference may now
appear at any depth in an array or object; it is no longer a separate top-level value category.

Run targets and historical reuse keep their author syntax. Names such as `build-output` are decoded
API vocabulary; the Markup tag remains `<build-record>`.

### Split WhisperX transcription from Narrative alignment

Speech transcription evidence and authored semantic alignment are separate graph operations in 0.4.
Replace each combined WhisperX Surface with an explicit evidence edge:

```svml
<import as="whisperx" from="@hypit/whisperx@1"/>
<import as="speechalign" from="@hypit/narrative-speech-alignment@1"/>

<whisperx:Transcription id="opening-transcription"
  media={opening-media.media} language="en"/>
<speechalign:Alignment id="opening-alignment" narrative={story}
  segment={story.segment.opening} domain={opening-media.domain}
  evidence={opening-transcription.transcript}/>
```

The WhisperX operation now returns `SpeechTranscriptEvidence`; the alignment operation returns
`NarrativeAlignment`. For an empty Segment, omit `evidence` from `<speechalign:Alignment>` and do not
declare a transcription request.

Update Runtime bindings from `@hypit/whisperx@1#whisperx-alignment` to
`@hypit/whisperx@1#whisperx-transcription`. `hypit transcribe` now writes an editable
`.transcript.svml` Source containing `<speech:Transcript>` rather than the earlier simplified JSON
view. Pass that SVML file to `hypit media grid --transcript` or import it from another Source and use
its published transcript record as the alignment `evidence` input.

## 3. Migrate an Author Package

### Construct terminal VisualTrack items explicitly

The terminal `VisualTrack` now carries one ordered `items` union instead of a `presents` field. A
package that emits only source-owning Presents should change the constructor name while keeping its
concise construction input:

```ts
import { sealPresentVisualTrack } from "@hypit/composition";

const track = sealPresentVisualTrack({
  id: "picture",
  timelineId: timeline.id,
  visualIr: "hypit.visual-ir@1",
  presents,
});
```

Use `sealVisualTrack({ items })` when the package intentionally emits the complete union. Every item
then states `kind: "present"` or `kind: "adjustment"`; Present owns a new source picture, while
Adjustment transforms the picture accumulated below its stack position. Consumers read
`track.items`, or use `visualPresents(track)` and `visualAdjustments(track)` when they need one
branch. Do not probe both `presents` and `items` or infer the branch from its payload.

The JavaScript boundary rejects a missing `items` array, an unknown item kind and a non-Present kind
passed to `sealPresentVisualTrack`. Rebuild project packages after updating this call; editing an
installed package copy is not a durable migration.

### Pass PreparedMedia directly to visual and audio components

All public media-materialization Producers and Capabilities are removed. A component Fragment accepts
`PreparedMedia` directly. Visual lowering projects its selected visual source and composes the member map
with the occurrence map. Audio lowering projects the selected audio source, preserves its preparation Map,
and quantizes occurrence facts only in `AudioProgram`:

```ts
// Visual Track component input
{ kind: "timed", media, extent }

// Audio Track terminal clip
{ source: { media }, sampling, window, mix }
```

Remove materialization inputs, Needs and Producer declarations from project packages. `HtmlProgram.videoSources`
now carries selected visual source facts and the exact TemporalMap; the visual Provider privately decodes them.
The audio renderer privately evaluates the selected audio member before mixing. Decoder formats, CFR/PCM working
files and caches are not graph values. A member map may still contain gaps: visual gaps are transparent and audio
gaps are silent, regardless of which member established the shared PreparedMedia domain.

Rendering selections now use `FrameSpan` and `timelineTypes.frameSpan` from `@hypit/timeline`.
The removed `MediaFrameRange` was not media metadata: it was a half-open interval on a finite frame
domain. Media, HTML and Provider packages may consume that interval, but must not redefine its
identity or basic validation. Timeline Author construction and HtmlProgram selections reuse the
same Type instead of publishing package-local `ConstructionSpan` or `HtmlFrameSpan` identities.
Caption timing, decoded-source windows and Studio's frame-bounded projections compose this same
primitive rather than restating its two fields as independent interval types.

`TemporalMap` no longer repeats `targetDomainId` and `sourceDomainId`. The first stage's `target.id`
and final stage's `source.id` are the endpoint identities, so a Map cannot carry two disagreeing
copies of the same fact:

```ts
sealTemporalMap({ stages: [{ target, source, pieces }] });
```

`MediaStreamSelection.policy` is also removed. The Selection retains only the selected stream indexes
and `spanAuthority`; names such as `primary-moving` and `default` belong to the request that performed
selection, not to the resulting selected-media fact.

### Declare one result per Producer

A Producer is one graph operation and now declares exactly one result: either a deterministic Output
or an external Need. Manifests also use direct Module references and Type names.

```ts
const manifest = {
  format: "hypit.module@1",
  ...moduleRef,
  dependencies: [dependencyModule],
  types: ["Request", "Result"],
  capabilities: [],
  producers: [{
    name: "render",
    inputs: [{ name: "request", type: requestType }],
    result: { kind: "output", name: "result", type: resultType },
  }],
} satisfies ModuleManifest;
```

Replace these 0.3 shapes:

| 0.3.1 | 0.4 |
| --- | --- |
| `dependencies: [{ module }]` | `dependencies: [module]` |
| `types: [{ name: "Result" }]` | `types: ["Result"]` |
| `outputs: [...]` plus `needs: [...]` | one discriminated `result` |
| a Producer used as a multi-result bag | separate Producers connected by explicit graph edges |

The handler returns the same single result declared by the manifest:

```ts
// Deterministic Output
return { kind: "output", value: { label: "ready" } };

// External request
return { kind: "need", constraints: completeModelRequest };
```

Remove `{ outputs, needs }`, the `{ kind: "inline", value }` wrapper, and code that reads
`context.producer`; the invoked Producer identity is already present in `context.command.producer`.

### Activate Producers and Refinements separately

`@hypit/hypit/admission` is replaced by `@hypit/hypit/refinement`. Structural Type checking remains a
framework responsibility; a Refinement is only the exact Type owner's semantic predicate.

```ts
import { createProducerPackageFacet } from "@hypit/hypit/producer";
import { createRefinementPackageFacet } from "@hypit/hypit/refinement";

export default {
  format: "hypit.package@1",
  modules: [{ manifest }],
  facets: [
    createProducerPackageFacet(component.producers ?? []),
    createRefinementPackageFacet(component.refinements ?? []),
  ],
};
```

The constructor arguments are arrays. Remove the old `{ producers, plannedNeeds }` and
`{ validators }` containers. Rename `TypeValidatorFacet` to `TypeRefinement`, `validators` to
`refinements`, and validation calls owned by the package to `refineValue` or `refineRecord` where
needed. `PlannedNeedFacet` and its pending-input presentation do not have a replacement: the plan
already carries unresolved Record edges, and a concrete Need exists only after all Producer inputs
exist.

### Use one recursive Value model

Replace `StoredValue` with `Value`, and `blobRefObjectSchema()` with `blobRefSchema()`. Do not branch
business logic into scalar, media and composite value categories. A `BlobRef` is a reserved leaf
inside the same recursive Value structure.

`ValueSchema` describes accepted data, not editor presentation. Remove `format: "color"` from string
schemas. If a Studio Inspector should render a color or structured control, put that hint on the
Companion's Inspector declaration instead:

```ts
{
  binding: "paint",
  control: "record",
  valuePresentation: {
    kind: "record",
    fields: { color: { kind: "color" } },
  },
}
```

Packages with no Studio Companion need no replacement presentation metadata.

## 4. Migrate Model and Provider packages

Generation no longer defines a universal request envelope, text/media/scalar port ontology, Model
registry, Provider choice or cross-model source-count limit. The Model package owns its complete
request Type, validation, exact Capability, result Type and request limits. A selected Endpoint may
apply narrower service limits without changing that Model contract.

For a new Model contract, use `@hypit/generation/model` and `defineModelModule()`. Existing
field-oriented packages may use the optional adapter at `@hypit/generation/model-fields`:

| 0.3.1 field-model API | 0.4 field adapter |
| --- | --- |
| `defineExactModelModule` | `defineFieldModelModule` |
| `createExactModelGenerationFragment` | `createFieldModelGenerationFragment` |
| `createExactModelPrimaryGenerationFragment` | `createFieldModelPrimaryFragment` |
| generic field limits treated as Generation rules | Model-owned field validation and defaults |

The field adapter is an implementation choice, not the protocol. Custom request structures can use
`defineModelModule()` directly. A Model never imports a Provider.

Providers depend one way on the exact Model Capability. The optional
`@hypit/generation/provider` helper now makes the pure/effect boundary explicit:

```ts
const plan = planWireRequest(mapping, completeRequest);
const wireRequest = await materializeWireRequest(plan, resolveUrl);
```

Custom multipart, uploaded-file-id or inline-byte adapters can implement their own mapping without
using this helper.

An Endpoint instance now has one authoritative `capabilities` list. Discovery and registration are
derived from that same list:

```ts
import { endpointOffers, installEndpoint } from "@hypit/hypit/endpoint";

const offers = endpointOffers(endpoint);
await installEndpoint(endpoint, registry);
```

Replace `endpoint.offers` and `endpoint.install(registry)`. Immediate handlers return `Value`
directly instead of `{ value: StoredValue }`; asynchronous `completed.result` does the same.
`EndpointCheckpoint` is now `{ status: "accepted" | "ended", handle, receipt? }` rather than an
optional `remoteEnded` flag.

`supports`, request-dependent scheduling and live pricing receive a concrete `EndpointRequest` only
after the Producer emits its Need. Remove `pendingInputs`. Before that point, planning has only an
`EndpointDemand` containing the exact Capability and return Type.

## 5. Migrate Source and Run Frontends

Custom adapters have smaller, direct return types:

| 0.3.1 | 0.4 |
| --- | --- |
| `SourceRange` from Protocol | `SourceRange` from `@hypit/source` |
| `SourceAssetResolver -> { artifact: BlobRef }` | `SourceAssetResolver -> BlobRef` |
| `RunFrontend.decode() -> { document }` | `RunFrontend.decode() -> RunDocument` |
| `RunFrontendSourceUnit` / `RunSourceUnit` | `SourceUnit` |
| `targets: [{ output }]` | `targets: [output]` |
| decoded candidate kind `provided` | `value` |
| decoded candidate kind `build-record` | `build-output` |

Only decoded API names change in the last two rows; official Markup remains `<value>` and
`<build-record>`.

## 6. Migrate compiler, Runtime and Result integrations

These APIs are usually implemented by a Distribution, not by a video project.

| 0.3.1 | 0.4 |
| --- | --- |
| `CompiledGraph` | `AuthorGraph` |
| `BuildTarget` wrappers | logical Output id strings |
| `BuildPlan.goals: { record, type }[]` | `BuildPlan.goals: RecordId[]` |
| `BuildPlan.outputBindings` | derive publication once outside Core |
| `BuildDefinition.initialRecords` and `.targets` | starting Records in `program`; publication in `PublicationPlan` |
| multi-record `ProducerAppliedFact` | one discriminated Output-or-Need result |
| persisted materialized Build state | immutable `BuildDefinition` plus ordered `BuildFact[]` |

Runtime stores and schedulers should persist Definition plus Facts and materialize `BuildState` as a
view. Result does not observe scheduler lifecycle. Synchronize it with accepted Records and Resource
access only:

```ts
await writer.sync({ records: state.records, resources });
```

Result creation uses one `PublicationPlan` as the authority for public name, logical Output, target
membership, Type and current-or-historical source:

```ts
const seed: BuildResultSeed = {
  id: buildId,
  sourceId,
  runId,
  publication: {
    outputs: [{
      name: "film",
      output: logicalOutputId,
      target: true,
      type: filmType,
      source: { kind: "current-record", record: recordId },
    }],
  },
  resourceReferences,
};
```

Replace `source: { id }`, `run: { id }`, `targets`, `publishedOutputs` and `forwards`. Historical reuse
is now an explicit publication source:

```ts
source: { kind: "historical-output", build: priorBuild, output: priorOutput }
```

Output descriptions report storage `representation` as `inline`, `file` or `value-document`.
Do not interpret those as domain categories; the nominal `type` remains separate. Finished Result
and Operation states are discriminated unions, so remove contradictory optional failure or terminal
fields instead of carrying them forward.

## 7. Update local media commands

The two frame-grid spellings are now one command with an explicit pagination choice:

| 0.3.1 | 0.4 |
| --- | --- |
| `hypit media tile … --to grid.jpg` | `hypit media grid … --to grid.jpg` |
| `hypit media tiles … --to grids` | `hypit media grid … --pages --to grids` |

`--ranges`, `--every-frame` and `--rows` are page operations and therefore require `--pages`.
Use `grid --waveform` to place amplitude beneath a video grid and `grid --spectrogram` to place
frequency-over-time evidence beneath it. The tracks are independent and may be combined. Standalone
`media waveform` and `media spectrogram` write PNGs from either audio or a video that contains audio.
Multiple audio streams require `--audio-stream <index>`; `media probe` reports the indexes.
Audio-only input is not a frame grid, and video without audio cannot produce either audio observation.
`--frame-marker-color <color>` changes the numbered sampled-frame lines on attached audio tracks.
Standalone views accept `--pixels-per-second`; waveform and spectrogram parameters remain separate.
Grid time labels remain the default. `--no-time` removes cell times, word-annotation times and an
attached audio track's time axis;
without `--transcript` or an attached audio track this is a picture-only grid. An attached audio track
retains the frame numbers that connect cells to its markers. `--header` independently adds the source name,
page range and frame count. Grid JSON now places these presentation choices under `view` and always
reports the resolved `source`; requested and actual frame times do not depend on visible labels.
Word context now adapts to the cell width unless `--word-context <n>` is selected. Paged grids accept
`--format png` for lossless output; a single grid follows its `.jpg`, `.jpeg` or `.png` destination.
Direct consumers of this package should update `@hypit/media-local` to `^0.3.0`.
Import the Runtime Provider from `@hypit/media-local`, local-file operations and observations from
`@hypit/media-local/files`, and the command contribution from `@hypit/media-local/cli`. The root
entry no longer re-exports file helpers. Import Video's command contribution from `@hypit/video/cli`;
the `@hypit/video` root retains application assembly and programmatic vocabulary queries.

## 8. Migrate Composition, Film and terminal audio graphs

Programmatic Composition construction no longer supplies one mixed `tracks` array. Split final
assembly into a recursive visual scope and root audio outputs:

```ts
sealComposition({
  id: "main",
  canvas,
  visual: { members: [{ kind: "track", id: "picture", track: picture }] },
  audio: [dialogue],
});
```

In SVML, every visual `<film:Track>` now requires a sibling-unique `id`, while an audio
`<film:Track>` has none. Sibling declaration order paints from back to front. The visual id names one placement rather than the reusable Track value;
the same VisualTrack can therefore appear in several Film scopes under different ids.
Remove whole-film placement from component occurrences and Recipes, then place the completed
VisualTrack at the parent Film or Stack. Use `<film:Stack id="...">` when several visual
Tracks must close into one local composite before entering the parent visual order. A Stack accepts
visual Tracks or nested Stacks; keep AudioTrack selections at the Film root.

Terminal `AudioTrack` now carries one closed `graph` instead of a top-level `clips` array. Plain clip
authors should construct its source-plus-mix subset with `audioGraphFromClips`. Consumers that only
observe source leaves can use `audioTrackClips`; components that combine or process sound should
connect graph nodes and publish another closed AudioTrack. Do not flatten an unknown process graph or
silently discard a process format.

Additive mix input declaration order no longer changes terminal identity. Mix inputs are
canonicalized as a multiset of signal references (duplicates are retained), while process port names
and effect-chain connections remain explicit and ordered where their semantics require it.
The Composition root follows the same additive law: equal AudioTrack ids are not routing keys, and
repeated closed signals remain repeated contributions. Execution-only clip ids derive from the root
occurrence path, so value identity is never overloaded as placement identity.

`@hypit/visual-adjustment` is the generic author package for HTML-backed color, blur, opacity and
affine picture adjustments. Pair it with Film Stack for a local visual group. `@hypit/audio-mix`
combines closed AudioTracks with explicit non-negative per-input gain. Neither package introduces a
central effect registry, implicit master processing or Track-name routing.

Visual and Audio Clip packages now use the same exact temporal relation model. Replace package-local
source-time objects with `TemporalRelationSpec` while authoring and `TemporalMap` after the target and
source domains are known. In markup this is the ordinary `Map` child. Omission means bounded partial
identity; it does not imply hold, loop or stretch.

Composition keeps a timed visual item's exact occurrence-local sampling Map separately from decoded
frame facts. Terminal AudioClip source nodes likewise keep an exact absolute `target`, exact `fadeIn`
and `fadeOut`, and an exact occurrence-local `sampling` Map separately from the source Artifact's
sample count. HTML compilation is the first visual frame-quantization boundary; AudioProgram
compilation is the first 48 kHz quantization boundary. Direct Composition consumers should stop
constructing pre-quantized frame/sample source ranges or treating those execution facts as the
temporal relation itself.

## 9. Make terminal delivery explicit

Programmatic HTML raster requests now require a `VisualDeliverySpec`. `TimelineVisual` records the
implemented visual requirement; `TimelineAudio` records its 48 kHz stereo PCM shape; final mux also
requires the complete `MediaDeliverySpec` and returns a `MuxedMedia` carrying it. Remove Provider-side
`quality` configuration and pass delivery through the author graph instead:

```ts
const delivery = htmlVideoDeliverySpec("standard");
const request = htmlRasterRequest(program, delivery.visual);
```

The ordinary `<html:Video>` Surface still needs no extra attribute: omission creates one private
standard BT.709 H.264/AAC MP4 requirement. Use `quality="draft|standard|high"` as its shorthand, or
pass `delivery={record}` from an author package that owns a complete `MediaDeliverySpec`. Runtime
Profiles continue to select browsers, executables, concurrency and budgets; they no longer choose
author-visible delivery quality.

Direct mux callers must provide the same delivery value that produced their `TimelineVisual`.
Mux rejects mismatched inputs rather than silently transcoding them.

Direct `rasterize-frames` callers must add an sRGB/full-range `picture: ImagePictureSpec` to
`HtmlFrameRequest`. Frame capture does not accept video codec, audio or container requirements, but
it no longer lets a Provider invent the color and matte policy. Its result is no longer a bare array:
read `{ picture, frames: [{ frame, artifact }] }` so stored frame Results retain both their pixel
interpretation and original absolute frame identities.

The local HTML Provider now selects its execution implementation explicitly. Existing profiles may
omit `renderer` and continue using the portable Chromium implementation. To use browser-side source
decode, Electron offscreen shared textures and WebCodecs H.264, configure an encoded-visual Endpoint:

```json
{
  "use": "@hypit/provider-html-local",
  "config": {
    "renderer": "electron",
    "electronPath": "/Applications/Electron.app/Contents/MacOS/Electron"
  }
}
```

Electron is user-managed and is never installed or chosen as a fallback. That Endpoint offers
`rasterize-visual` only; configure a separate Chromium Endpoint when Studio or another consumer also
needs `rasterize-frames`. The Electron path removes PNG from both source-video input and composed-video
output. FFmpeg remains in that path only for H.264-to-MP4 muxing and output inspection.

## 10. Verify the migrated project

After updating source code and the lockfile:

1. Rebuild every changed project package from its source.
2. Run that package's typecheck and tests.
3. Run `hypit check` on the actual Source and Run.
4. Run `hypit plan <run> --runtime <profile>` and inspect targets, selected Candidates, blocked Record
   dependencies, the chosen Endpoint and its support evidence.
5. Use `hypit pricing` when external work may incur a charge.
6. Review the production in Studio before authorizing a Build.

Do not regenerate accepted media merely to test the migration. If a required third-party Author or
Provider package has no 0.4-compatible release and a source migration is not in scope, keep that
production on its locked 0.3.1 installation until the package can be migrated.
