# 将现有项目升级到 0.4

[English](0.4.md)

从 0.3.1 升级视频项目、Author Package、Provider、Runtime 集成或 Result 集成时，请阅读本文。
更旧的项目应先完成 [0.3 项目迁移](0.3.zh-CN.md)和
[0.3.1 SDK 迁移](0.3.1.zh-CN.md)。

0.4 改变了框架 SDK 和持久化 Result 的结构，但不会重新解释作品的创作意图。只使用已发布包的
普通 `.svml`、`.svs`、`.svrun` 项目，通常只需要整体更新兼容依赖、按需修改一处 `<value>`
文件格式并验证真实作品。自行构造图，或接入 Model、Endpoint、Runtime、Result API 的包，则需要
迁移下文相应的边界。

## 判断哪些部分与项目有关

| 项目内容 | 需要检查的部分 |
| --- | --- |
| 只有 Sources、Recipes 和 Runs | 保留现有 Results，更新锁定的安装，检查 `<value>` 文件，然后验证真实作品 |
| 项目 `packages/` 或其他 Author Package | 还要迁移 Manifest、Producer 结果、Refinement 和 Studio 展示提示 |
| Model 或 Provider 包 | 还要迁移 Model 自有请求和统一的 Endpoint capability 声明 |
| 自定义 Source/Run Frontend | 还要迁移更直接的 Source、Run 适配器返回类型 |
| 自定义 Compiler、Runtime 或 Result Repository | 还要迁移 Author Graph、Build Definition/Facts 和 Publication Plan API |

不要只更新全局可执行文件。项目 lockfile 和所有直接选择的包必须共同解析为一组兼容版本。沿用
项目现有的包管理器；Hypit 不另造 package lock，也不会在构建期间自动升级包。

## 1. 更改安装前先保留已接受的成果

0.4 继续使用 `@1` 公共格式标识，但不会猜测已经淘汰的 0.3 Result 结构。因此，0.4 的
Repository Reader 不会按形状导入旧 `result.json`。更新前：

1. 用 `hypit version` 和 `hypit paths` 记录当前可工作的可执行文件和项目位置。
2. 在迁移完成前，保留可恢复的 0.3.1 lockfile 和安装。
3. 趁 0.3.1 仍能读取旧 Result，导出所有需要跨版本保留的已接受 Output：

   ```sh
   hypit get <build-id> --output <name> --to <path>
   ```

4. 把原 Result 目录作为历史保留，不要手工改写其中的 Manifest。

导出的媒体和值文档仍然是普通项目输入。在 0.4 Run 中通过 `<file>` 或 `<value>` 显式引用；
只有用户确实需要新成果时才重新 Build。除非 Result 已经由新结构产生，否则旧 0.3 Build id
不能作为 0.4 `<build-record>` 的来源。

## 2. 更新普通视频项目

一起更新项目已有的 Hypit 依赖和 lockfile。重新安装并重新构建项目包；不要把修改生成的
`dist` 或 `node_modules` 当作长期修复。

官方 Run 语法仍使用 `<value>`、`<file>` 和 `<build-record>`。`<value from="...">` 引用的
JSON 文件现在直接包含图的 Value，需要去掉旧 `StoredValue` 包装：

```json
{ "kind": "inline", "value": { "enabled": true, "strength": 0.8 } }
```

改为：

```json
{ "enabled": true, "strength": 0.8 }
```

字符串、数字、布尔值、null、数组和对象都遵循同一规则。Blob 引用现在可以出现在数组或对象的
任意深度，不再是独立的顶层值类别。

Run target 和历史复用的创作语法保持不变。`build-output` 是解码后的 API 词汇，Markup 标签仍是
`<build-record>`。

### 分开 WhisperX 转写与 Narrative 对齐

0.4 把语音转写证据和作者语义对齐表达为两个独立图操作。把原先合并的 WhisperX Surface 改为
显式证据边：

```svml
<import as="whisperx" from="@hypit/whisperx@1"/>
<import as="speechalign" from="@hypit/narrative-speech-alignment@1"/>

<whisperx:Transcription id="opening-transcription"
  media={opening-media.media} language="en"/>
<speechalign:Alignment id="opening-alignment" narrative={story}
  segment={story.segment.opening} domain={opening-media.domain}
  evidence={opening-transcription.transcript}/>
```

WhisperX 操作现在返回 `SpeechTranscriptEvidence`；对齐操作返回 `NarrativeAlignment`。对于没有
Token 的 Segment，`<speechalign:Alignment>` 省略 `evidence`，也不声明转写请求。

把 Runtime binding 从 `@hypit/whisperx@1#whisperx-alignment` 更新为
`@hypit/whisperx@1#whisperx-transcription`。`hypit transcribe` 现在写出可编辑的
`.transcript.svml` Source，其中包含 `<speech:Transcript>`，不再写早期的简化 JSON 视图。
该 SVML 文件可以传给 `hypit media grid --transcript`，也可以被其他 Source 导入，并将其发布的
transcript record 显式连接到 Alignment 的 `evidence` 输入。

## 3. 迁移 Author Package

### 显式构造终端 VisualTrack items

终端 `VisualTrack` 现在携带一条有序的 `items` 联合，不再保留 `presents` 字段。只产生自有 source
画面的 Present 包，可以保留简洁的构造输入，只修改构造器名称：

```ts
import { sealPresentVisualTrack } from "@hypit/composition";

const track = sealPresentVisualTrack({
  id: "picture",
  timelineId: timeline.id,
  visualIr: "hypit.visual-ir@1",
  presents,
});
```

包需要有意产生完整联合时，使用 `sealVisualTrack({ items })`。每个 item 显式声明
`kind: "present"` 或 `kind: "adjustment"`：Present 拥有新的主要 source picture，Adjustment
变换其栈位置以下已经累计的 Picture。消费方统一读取 `track.items`；只需要某一分支时，使用
`visualPresents(track)` 或 `visualAdjustments(track)`。不要同时试探 `presents` 与 `items`，也不要
根据 payload 猜测分支。

JavaScript 边界会拒绝缺失的 `items` 数组、未知 item kind，以及传给 `sealPresentVisualTrack`
的非 Present kind。修改调用后应重新构建项目 package；直接修改已安装包副本不是可持续迁移。

### 将 PreparedMedia 直接交给视听组件

所有公开媒体物化 Producer 与 Capability 均已删除。组件 Fragment 直接接受 `PreparedMedia`。
视觉 lowering 投影所选 visual source，并把 member Map 与 occurrence Map 组合；音频 lowering
把 PreparedMedia source 与 occurrence Map 保留到 `AudioProgram`：

```ts
// Visual Track 组件输入
{ kind: "timed", media, extent }

// Audio Track 终端 Clip
{ source: { media }, sampling, window, mix }
```

项目包应删除物化输入、Need 与 Producer 声明。`HtmlProgram.videoSources` 直接携带所选画面源事实与精确
TemporalMap，由视觉 Provider 私下解码；音频 Renderer 在混音前私下求值所选音频成员。解码格式、CFR／PCM
工作文件和缓存都不是图值。Member Map 仍可包含空洞：视觉空洞为透明，音频空洞为静音，与哪个成员决定
PreparedMedia 的共享时域无关。

渲染区间现在统一使用 `@hypit/timeline` 的 `FrameSpan` 与 `timelineTypes.frameSpan`。
已删除的 `MediaFrameRange` 不是媒体元信息，而是有限帧域上的半开区间。Media、HTML 与 Provider
可以消费这个区间，但不再各自定义其身份与基础校验。Timeline Author 的构造图与 HtmlProgram 的渲染选区
也复用同一个 Type，不再发布包私有的 `ConstructionSpan` 或 `HtmlFrameSpan` 身份。Caption timing、
解码源窗口和 Studio 的帧区间投影也组合该原语，不再各自重述一份独立区间类型。

`TemporalMap` 不再重复携带 `targetDomainId` 与 `sourceDomainId`。首个 stage 的 `target.id`
和最后一个 stage 的 `source.id` 就是 Map 的端点身份，因此同一事实不会出现两份可能不一致的副本：

```ts
sealTemporalMap({ stages: [{ target, source, pieces }] });
```

`MediaStreamSelection.policy` 也已删除。Selection 只保留实际选中的流索引和 `spanAuthority`；
`primary-moving`、`default` 等名称属于执行选择的请求，不属于选择完成后的媒体事实。

### 每个 Producer 只声明一个结果

一个 Producer 就是一个图操作，现在只声明一个结果：确定性 Output 或外部 Need 二选一。
Manifest 也直接使用 Module 引用和 Type 名称。

```ts
const manifest = {
  format: "hypit.module@1",
  ...moduleRef,
  dependencies: [dependencyModule],
  types: ["Request", "Result"],
  capabilities: [],
  producers: [{
    name: "render",
    inputs: [{ name: "request", type: requestType }],
    result: { kind: "output", name: "result", type: resultType },
  }],
} satisfies ModuleManifest;
```

替换以下 0.3 结构：

| 0.3.1 | 0.4 |
| --- | --- |
| `dependencies: [{ module }]` | `dependencies: [module]` |
| `types: [{ name: "Result" }]` | `types: ["Result"]` |
| `outputs: [...]` 加 `needs: [...]` | 一个可判别的 `result` |
| 把 Producer 当成多结果容器 | 拆成由显式图边连接的多个 Producer |

Handler 返回 Manifest 中声明的同一个单结果：

```ts
// 确定性 Output
return { kind: "output", value: { label: "ready" } };

// 外部请求
return { kind: "need", constraints: completeModelRequest };
```

删除 `{ outputs, needs }`、`{ kind: "inline", value }` 包装，以及读取 `context.producer` 的代码；
被调用的 Producer 身份已经在 `context.command.producer` 中。

### 分别激活 Producer 和 Refinement

`@hypit/hypit/admission` 被 `@hypit/hypit/refinement` 取代。结构性 Type 检查仍由框架负责；
Refinement 只表达精确 Type 所有者的语义谓词。

```ts
import { createProducerPackageFacet } from "@hypit/hypit/producer";
import { createRefinementPackageFacet } from "@hypit/hypit/refinement";

export default {
  format: "hypit.package@1",
  modules: [{ manifest }],
  facets: [
    createProducerPackageFacet(component.producers ?? []),
    createRefinementPackageFacet(component.refinements ?? []),
  ],
};
```

两个构造器都接收数组。删除旧 `{ producers, plannedNeeds }` 和 `{ validators }` 容器。把
`TypeValidatorFacet` 改为 `TypeRefinement`，`validators` 改为 `refinements`；包自身需要调用时，
改用 `refineValue` 或 `refineRecord`。`PlannedNeedFacet` 及其 pending-input 展示没有替代品：
Plan 本来就保留未解析的 Record 边，而具体 Need 只能在 Producer 的所有输入已经存在后产生。

### 使用一个递归 Value 模型

把 `StoredValue` 替换为 `Value`，把 `blobRefObjectSchema()` 替换为 `blobRefSchema()`。不要再把业务
逻辑分成 scalar、media、composite 等值类别。`BlobRef` 是同一个递归 Value 结构中的保留叶子。

`ValueSchema` 描述可接受的数据，不描述编辑器展示。删除字符串 Schema 上的 `format: "color"`。
如果 Studio Inspector 应使用颜色或结构化控件，请把提示放到 Companion 的 Inspector 声明：

```ts
{
  binding: "paint",
  control: "record",
  valuePresentation: {
    kind: "record",
    fields: { color: { kind: "color" } },
  },
}
```

没有 Studio Companion 的包不需要补充任何展示元信息。

## 4. 迁移 Model 和 Provider 包

Generation 不再定义通用请求信封、text/media/scalar 端口本体、Model Registry、Provider 选择，
也不定义跨模型的来源数量限制。Model 包拥有完整请求 Type、校验、精确 Capability、结果 Type
和请求限制。选定的 Endpoint 可以施加更窄的服务限制，但不会改变 Model contract。

新的 Model contract 使用 `@hypit/generation/model` 和 `defineModelModule()`。现有字段式包可使用
`@hypit/generation/model-fields` 的可选适配器：

| 0.3.1 字段式 Model API | 0.4 字段适配器 |
| --- | --- |
| `defineExactModelModule` | `defineFieldModelModule` |
| `createExactModelGenerationFragment` | `createFieldModelGenerationFragment` |
| `createExactModelPrimaryGenerationFragment` | `createFieldModelPrimaryFragment` |
| 把通用字段限制当作 Generation 规则 | Model 自有的字段校验和默认值 |

字段适配器只是实现选择，不是协议。自定义请求结构可以直接使用 `defineModelModule()`。Model
永远不导入 Provider。

Provider 单向依赖它实现的精确 Model Capability。可选的 `@hypit/generation/provider` helper
现在明确分开纯投影和副作用：

```ts
const plan = planWireRequest(mapping, completeRequest);
const wireRequest = await materializeWireRequest(plan, resolveUrl);
```

自定义 multipart、已上传文件 id 或内联字节适配器可以自行实现，不必使用该 helper。

Endpoint instance 现在只有一份权威 `capabilities` 列表，发现和注册都从它派生：

```ts
import { endpointOffers, installEndpoint } from "@hypit/hypit/endpoint";

const offers = endpointOffers(endpoint);
await installEndpoint(endpoint, registry);
```

替换 `endpoint.offers` 和 `endpoint.install(registry)`。Immediate handler 直接返回 `Value`，不再
返回 `{ value: StoredValue }`；异步的 `completed.result` 同理。`EndpointCheckpoint` 现在是
`{ status: "accepted" | "ended", handle, receipt? }`，不再使用可选 `remoteEnded` 标志。

`supports`、按请求计算的调度和实时定价，只在 Producer 发出 Need 后接收具体
`EndpointRequest`。删除 `pendingInputs`。在此之前，Plan 只有包含精确 Capability 和返回 Type
的 `EndpointDemand`。

## 5. 迁移 Source 和 Run Frontend

自定义适配器改用更小、更直接的返回类型：

| 0.3.1 | 0.4 |
| --- | --- |
| 从 Protocol 导入 `SourceRange` | 从 `@hypit/source` 导入 `SourceRange` |
| `SourceAssetResolver -> { artifact: BlobRef }` | `SourceAssetResolver -> BlobRef` |
| `RunFrontend.decode() -> { document }` | `RunFrontend.decode() -> RunDocument` |
| `RunFrontendSourceUnit` / `RunSourceUnit` | `SourceUnit` |
| `targets: [{ output }]` | `targets: [output]` |
| 解码后的 candidate kind `provided` | `value` |
| 解码后的 candidate kind `build-record` | `build-output` |

最后两行只改变解码后的 API 名称；官方 Markup 仍使用 `<value>` 和 `<build-record>`。

## 6. 迁移 Compiler、Runtime 和 Result 集成

这些 API 通常由 Distribution 实现，而不是视频项目实现。

| 0.3.1 | 0.4 |
| --- | --- |
| `CompiledGraph` | `AuthorGraph` |
| `BuildTarget` 包装 | 逻辑 Output id 字符串 |
| `BuildPlan.goals: { record, type }[]` | `BuildPlan.goals: RecordId[]` |
| `BuildPlan.outputBindings` | 在 Core 外只派生一次 publication |
| `BuildDefinition.initialRecords` 和 `.targets` | 起始 Records 归入 `program`；发布归入 `PublicationPlan` |
| 多 Record 的 `ProducerAppliedFact` | 单个可判别的 Output 或 Need 结果 |
| 持久化实体化 Build state | 不可变 `BuildDefinition` 加有序 `BuildFact[]` |

Runtime Store 和 Scheduler 应持久化 Definition 加 Facts，把 `BuildState` 作为读取视图实体化。
Result 不观察 Scheduler 生命周期，只使用已接受 Records 和 Resource 访问进行同步：

```ts
await writer.sync({ records: state.records, resources });
```

创建 Result 时，用一份 `PublicationPlan` 统一决定公共名称、逻辑 Output、是否为 target、Type，
以及当前或历史来源：

```ts
const seed: BuildResultSeed = {
  id: buildId,
  sourceId,
  runId,
  publication: {
    outputs: [{
      name: "film",
      output: logicalOutputId,
      target: true,
      type: filmType,
      source: { kind: "current-record", record: recordId },
    }],
  },
  resourceReferences,
};
```

替换 `source: { id }`、`run: { id }`、`targets`、`publishedOutputs` 和 `forwards`。历史复用现在是
显式 publication source：

```ts
source: { kind: "historical-output", build: priorBuild, output: priorOutput }
```

Output description 用 `inline`、`file`、`value-document` 表示存储 `representation`。不要把它们
解释成领域类别；名义 `type` 与其分离。Finished Result 和 Operation state 是可判别联合，因此
应删除互相矛盾的可选 failure 或 terminal 字段，不要原样保留。

## 7. 更新本地媒体命令

两种帧网格写法合并为一个命令，分页改为显式选择：

| 0.3.1 | 0.4 |
| --- | --- |
| `hypit media tile … --to grid.jpg` | `hypit media grid … --to grid.jpg` |
| `hypit media tiles … --to grids` | `hypit media grid … --pages --to grids` |

`--ranges`、`--every-frame` 和 `--rows` 属于分页操作，因此必须配合 `--pages`。
用 `grid --waveform` 把振幅放在视频网格下方，用 `grid --spectrogram` 把频率随时间的证据放在下方。
两条轨道彼此独立，也可以同时使用。独立的 `media waveform` 和 `media spectrogram` 都能从音频文件
或含音轨的视频输出 PNG。存在多条音频流时，必须用
`--audio-stream <index>` 显式选择；`media probe` 会列出这些索引。纯音频不是帧网格，
没有音轨的视频也不能产生这两种音频观察。
`--frame-marker-color <color>` 可更改附着音频轨道上带编号的采样帧竖线颜色。
独立视图支持 `--pixels-per-second`；波形与频谱的参数互不混用。
网格默认显示时间标签。`--no-time` 会移除单元格时间、词语注释里的数字时间以及附着
音频轨道的时间轴；未提供 `--transcript` 或附着音频轨道时得到纯图片网格。附着音频轨道仍会保留
连接单元格与标记的帧编号。`--header` 独立添加来源名称、页面区间和帧数。
网格 JSON 现在把这些呈现选择放在 `view` 下，并始终报告解析后的 `source`；请求时间和
实际解码时间不依赖可见标签。
词语上下文现在会根据单元格宽度自动调整，也可以用 `--word-context <n>` 显式指定。分页网格可用
`--format png` 输出无损图片；单张网格遵循目标文件的 `.jpg`、`.jpeg` 或 `.png` 扩展名。
直接依赖该包的项目应把 `@hypit/media-local` 更新到 `^0.3.0`。
Runtime Provider 从 `@hypit/media-local` 导入，本地文件操作与观察从
`@hypit/media-local/files` 导入，命令贡献从 `@hypit/media-local/cli` 导入；根入口不再转发
文件辅助函数。Video 的命令贡献从 `@hypit/video/cli` 导入；`@hypit/video` 根入口保留应用组装与
程序化 vocabulary 查询。

## 8. 迁移 Composition、Film 与终端音频图

通过 API 构造 Composition 时，不再提供一个混合的 `tracks` 数组。最终装配分为递归视觉 Scope 和根音频输出：

```ts
sealComposition({
  id: "main",
  canvas,
  visual: { members: [{ kind: "track", id: "picture", track: picture }] },
  audio: [dialogue],
});
```

SVML 中每个视觉 `<film:Track>` 现在都要求同级唯一的 `id`，音频 `<film:Track>` 不带视觉 id。
同级声明顺序从后到前绘制。
视觉 id 命名的是一次放置，而不是可复用 Track 值本身；因此同一个 VisualTrack 可以通过不同 id 放入多个
Film scope。从组件 occurrence 与
Recipe 中删除整片放置信息，再由父 Film 或 Stack 放置完成后的 VisualTrack。若若干 VisualTrack 需要先闭合
成一张局部画面，再进入父级视觉顺序，使用 `<film:Stack id="...">`。Stack 只接受 VisualTrack 或
嵌套 Stack；AudioTrack 选择留在 Film 根上。

终端 `AudioTrack` 现在携带一个闭合 `graph`，不再直接暴露顶层 `clips` 数组。只制作普通 Clip 的包可用
`audioGraphFromClips` 构造 source + mix 子集；只观察来源叶子的消费者可用 `audioTrackClips`。需要组合或处理
声音的组件应连接图节点，再发布一个新的闭合 AudioTrack；不能把未知 Process 图拍平，也不能静默丢弃
Process format。

加法混音输入的声明顺序不再改变终端身份。Mix 输入按 signal reference 的多重集合规范化（重复引用会保留）；
Process 端口名与效果链连接仍然显式存在，并在语义要求处保持顺序。
Composition 根也遵循同一加法规律：相同 AudioTrack id 不是路由键，重复闭合信号仍是重复贡献。
仅供执行的 Clip id 从根出现路径派生，不再把值身份兼作放置身份。

`@hypit/visual-adjustment` 是 HTML 调色、模糊、透明度与仿射画面调整的通用作者包；需要局部作用域时与 Film
Stack 组合。`@hypit/audio-mix` 用显式的非负输入 gain 组合闭合 AudioTrack。两者都不引入中央效果注册表、
隐式 Master 处理或按 Track 名寻址。

Visual 与 Audio Clip 包现在使用同一套精确时间关系模型。作者声明改用 `TemporalRelationSpec`，在 target/source
有限域已知后解析为 `TemporalMap`，不再各自维护 source-time 对象。Markup 中对应普通的 `Map` 子项。省略 Map
表示有界的部分恒等映射，不隐含 hold、loop 或 stretch。

Composition 将 timed visual item 的精确 occurrence-local sampling Map 与解码帧事实分开保存。终端 AudioClip
source node 同样分别保存精确绝对 `target`、精确 `fadeIn`/`fadeOut`、精确 occurrence-local `sampling` Map，
以及源 Artifact 的样本数。HTML 编译是画面第一次量化到帧的边界；AudioProgram 编译是声音第一次量化到
48 kHz 的边界。直接构造 Composition 的消费者应删除预先量化的源帧/样本区间，不再把执行事实当作时间关系本身。

## 9. 显式声明终端交付要求

程序化 HTML 光栅请求现在必须提供 `VisualDeliverySpec`。`TimelineVisual` 记录自己实现的视觉要求，
`TimelineAudio` 记录 48 kHz stereo PCM 形状；最终 mux 还必须取得完整的 `MediaDeliverySpec`，返回值
`MuxedMedia` 也会携带它。删除 Provider 配置中的 `quality`，把交付要求放入作者图：

```ts
const delivery = htmlVideoDeliverySpec("standard");
const request = htmlRasterRequest(program, delivery.visual);
```

普通 `<html:Video>` 无需增加属性：省略时会在作者图中形成一份私有的标准 BT.709 H.264/AAC MP4
要求。可以用 `quality="draft|standard|high"` 简写，也可以由拥有完整 `MediaDeliverySpec` 的作者包传入
`delivery={record}`。Runtime Profile 继续选择浏览器、可执行文件、并发和预算，不再选择作者可见的
交付质量。

直接调用 mux 时必须传入生成该 `TimelineVisual` 的同一份 delivery。输入不一致会明确失败，不会静默转码。

直接调用 `rasterize-frames` 时，需要在 `HtmlFrameRequest` 中增加 sRGB/full-range 的
`picture: ImagePictureSpec`。逐帧图片不接受视频 codec、音频或 container 要求，但也不再允许 Provider
自行决定色彩和 matte 政策。返回值不再是裸数组；应读取
`{ picture, frames: [{ frame, artifact }] }`，使保存后的逐帧 Result 仍保有像素解释和原始绝对帧身份。

本地 HTML Provider 现在显式选择执行实现。现有 Profile 可以省略 `renderer`，继续使用便携的 Chromium
实现。若要启用浏览器内源视频解码、Electron offscreen shared texture 和 WebCodecs H.264，需要配置一个
encoded-visual Endpoint：

```json
{
  "use": "@hypit/provider-html-local",
  "config": {
    "renderer": "electron",
    "electronPath": "/Applications/Electron.app/Contents/MacOS/Electron"
  }
}
```

Electron 由部署方管理，不会被自动安装或作为 fallback 选择。该 Endpoint 只提供 `rasterize-visual`；若
Studio 或其他消费者还需要 `rasterize-frames`，应另配一个 Chromium Endpoint。Electron 路径同时删除了
源视频输入和合成视频输出两侧的 PNG；其中 FFmpeg 只负责把 H.264 封装为 MP4，以及检查最终输出。

## 10. 验证迁移后的项目

更新源码和 lockfile 后：

1. 从源码重新构建所有改过的项目包。
2. 运行这些包自己的 typecheck 和测试。
3. 对真实 Source 和 Run 执行 `hypit check`。
4. 执行 `hypit plan <run> --runtime <profile>`，检查 targets、选中的 Candidates、被阻塞的 Record
   依赖、选定的 Endpoint 及其支持证据。
5. 外部工作可能收费时执行 `hypit pricing`。
6. 在授权 Build 之前，到 Studio 审阅作品。

不要为了测试迁移而重新生成已经接受的媒体。如果必须使用的第三方 Author 或 Provider 包还没有
0.4 兼容版本，而当前范围又不包括源码迁移，就让该作品继续使用锁定的 0.3.1 安装，直到依赖包
完成迁移。
