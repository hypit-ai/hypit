# 将现有项目升级到 Hypit 0.4

[English](0.4.md)

本文用于把 0.3.1 项目或框架集成迁移到 0.4。更早的项目应先按照
[0.3](0.3.zh-CN.md) 与 [0.3.1](0.3.1.zh-CN.md) 指南到达 0.3.1。

Hypit 0.4 只有一套当前 Author、Target 选择、Build 与 Result 模型，发行版只有一条执行路径。
项目 Source 和包代码应迁移到当前接口；迁移期间若使用了本地转换脚本，迁移完成后应删除。

转换脚本可以一次性改写项目文件，但不能成为 Author Package、frontend、Runtime adapter 或常驻命令。
它的输出必须已经是普通的当前 Source 与项目资源；迁移完成后不保留兼容对象或另一条执行路径。

## 判断受影响的边界

| 项目内容 | 需要检查 |
| --- | --- |
| `.svml`、`.svs` 和素材 | 保留已接受媒体、更新锁定安装、把长期材料选择放进 Author Source，然后验证真实作品 |
| 项目 `packages/` 或其他 Author Package | 迁移 declaration、Manifest、Producer 结果、Refinement、PreparedMedia 输入和 Studio Companion |
| Model 或 Provider 包 | 保持请求 contract 由 Model 所有，迁移 Endpoint capability 和结果接口 |
| 自定义 Source frontend | 直接返回当前 source-neutral 文档结构 |
| Compiler、Runtime 或 Result 集成 | 一起迁移 AuthorGraph、Target 选择、Build Definition/Facts、ResultIntent 和当前 Result schema |

应把项目依赖与 lockfile 作为一组共同更新。项目包应从源码重新构建；修改 `dist/` 或
`node_modules/` 不是迁移结果。

## 1. 升级前保留已接受成果

0.4 保持公共协议标识为 `@1`，但其中的当前结构已经变化。Result reader 只读取当前
`hypit.build-result@1` schema。更改安装前：

1. 用 `hypit version` 和 `hypit paths` 记录实际可工作的可执行文件与项目路径。
2. 迁移期间保留可恢复的 0.3.1 lockfile 和安装。
3. 用该安装导出项目仍需使用的全部已接受 Output：

   ```sh
   hypit get <build-id> --output <name> --to <project-path>
   ```

4. 把旧 Result 目录作为历史保留，不手工改写其中的 Manifest。

导出的图像、视频、音频或证据文档都是普通项目资源。0.4 中由所属包的 Author declaration
赋予它 Type 和含义；新作品不需要旧 Build 地址才能使用该资源。

## 2. 把执行选择放回当前所有者

Author Source 拥有作品与长期材料引用。每次命令显式选择本次执行需要的公共 Target：

```sh
hypit check main.svml
hypit plan main.svml --target final.video
hypit build main.svml --target final.video --follow
```

需要多个 Output 时重复 `--target`。若项目需要更短的重复命令，使用普通任务运行器或 package script；
不要另建 Target 文件、默认 Target 或注册表。

被接受的生成文件成为普通项目素材，由消费者直接引用：

```svml
<import as="asset" from="@hypit/media@1"/>
<import as="mediaop" from="@hypit/media-operations@1"/>

<asset:Video id="accepted-opening" src="./assets/opening.mp4"/>
<mediaop:Prepare id="opening-media" source={accepted-opening}
  video="primary-moving" audio="default" span-authority="video"/>
```

如需请求一次新生成，Target `opening-generation.video`。Build 会把生成材料作为 package-owned
artifact 保留；是否采用它仍由之后修改消费者引用决定。

## 3. 显式保留语音证据

语音转写与作者语义对齐是两个独立操作：

```svml
<whisperx:Transcription id="opening-transcription"
  media={opening-media.media} language="en"/>
<speechalign:Alignment id="opening-alignment" narrative={story}
  segment={story.segment.opening} domain={opening-media.domain}
  evidence={opening-transcription.transcript}/>
```

`hypit transcribe` 写出包含 `SpeechTranscriptEvidence` 的可编辑 `.transcript.svml` Source。
在线转写与外部证据因此以同一个 Type 进入 Alignment。证据文件可以被理解和修正，而不改变作者
真正表达的语义意图。

## 4. 迁移 Author Package

### Declaration 与值

Author package 编译 syntax-neutral declaration。Package compiler 拥有 declaration 语义，Frontend
拥有文本语法。值统一使用递归 `Value`，其中 `BlobRef` 是保留叶子。把 `StoredValue` 改为
`Value`，把 `blobRefObjectSchema()` 改为 `blobRefSchema()`。

`ValueSchema` 描述可接受数据，不描述 Studio 展示。颜色选择器等控件提示归属 package 的
Studio Companion。

### 每个 Producer 一个结果

一个 Producer 只声明一个结果：确定性 Output 或外部 Need 二选一。

```ts
const manifest = {
  format: "hypit.module@1",
  ...moduleRef,
  dependencies: [dependencyModule],
  types: ["Request", "Result"],
  capabilities: [],
  producers: [{
    name: "render",
    inputs: [{ name: "request", type: requestType }],
    result: { kind: "output", name: "result", type: resultType },
  }],
} satisfies ModuleManifest;
```

Handler 根据声明返回 `{ kind: "output", value }` 或 `{ kind: "need", constraints }`。旧的多结果
操作应拆为由显式图边连接的多个 Producer。

### Refinement

结构性 Type 校验属于框架。Package Refinement 只表达精确 Type 所有者的语义谓词：

```ts
createProducerPackageFacet(component.producers ?? [])
createRefinementPackageFacet(component.refinements ?? [])
```

使用 `TypeRefinement`、`refinements`、`refineValue` 和 `refineRecord`。只有在 Producer 输入全部
存在后才产生具体 Need；Plan 本身已经保留受阻的 Record 依赖。

### Prepared media 与视听结构

视觉和音频组件直接接受 `PreparedMedia`。Preparation 保留实际选择的 source 事实与局部
TemporalMap；occurrence sampling 与该 Map 组合。解码工作文件、CFR／PCM 中间物和缓存留在执行
Provider 内部。

静态图片现在与 prepared video、compositable surface 使用同一种显式画面解释。为
`visual:Clip image={...}` 或静态图片 `deck:Card source={...}` 增加 `picture="srgb"`；
Prepared 含时媒体和 Surface 不接受这个字段。Blob 与 extent 本身不能说明 primaries、transfer、
range、sample bit depth 或 alpha 语义。

公开交付画面类型为 `OutputPictureSpec`、`VideoOutputPictureSpec` 和 `FrameOutputPictureSpec`。
`PictureObservation` 记录源标签，`PictureInterpretation` 记录准备时选择的解释。Prepare 接受
`source` 或 `sdr-bt709`，成片使用 BT.709 H.264 家族。

终端视觉结构是由 Track、Stack 与 Process member 构成的有序递归 `VisualScope`；每个 VisualTrack
内部再拥有有序的 `present`、含时 `process` 与 `adjustment` item。视觉 z-order 属于 scope 中的
occurrence，而不属于可复用视觉组件。Transition 是两个 Clip Window 精确交集上的显式关系，并降低为
Track 内的含时 Process。`VisualTransitionEffect` 现在是端口严格为 `outgoing`、`incoming` 的闭合
`VisualProcessEffect`；TypeScript 直接构造的效果与保存值都应携带 `{ inputs, program }`，不再传递裸
Visual Program。

sibling matte 使用 `@hypit/visual-matte` Effect，并由 `<film:Process>` 与具名的 `content`、`matte`
Input 装配。`channel="alpha|luminance"` 与 `invert="true|false"` 都是显式效果选择。每个 Input 都是
递归视觉 Scope；Process 在父 Scope 中只占一个绘制位置，并消费输入，而不会把输入再次作为父级 sibling
绘制。不要把这项关系编码进 Track id 或 z-order。音频保持独立求值图，最终混入 Film 的 Audio Program。

`Composition` 现在拥有唯一 Timeline；HTML、音频与视频编译不再接收第二份 `timeline` 输入。

逐帧空间区域统一使用 `@hypit/spatial-sequence`。把作者接受的序列保存在普通 SVML Source 中，
通过 opaque `<sequence:Regions>` JSON 正文发布。`RegionSequenceDocument` 明确声明 Clock、帧数以及
每一帧在最终画面中的规范化 region 或 `null`。主 Source 用
`<sequence:TimelineRegions document={...} timeline={...} canvas={...}/>` 显式附着；Clock 与帧数必须
完全一致。Caption 再用
`<caption-fine:Follow role="..." series="..." missing="hide|authored-placement"/>` 声明自己的使用关系。
检测、身份关联、插值和修订都在作者文件进入 Build 之前完成。

半开帧区间统一使用 `@hypit/timeline` 的 `FrameSpan`。`TemporalMap` 的端点身份来自首个 target
domain 和最终 source domain，不再复制端点 id 元数据。

### Studio Companion

Companion 投影作者对象、Timeline Item、preview hint 和 Inspector 控件，不制造第二套作品模型。
Item id 只在所属 Track 内有效，跨边界时由 Studio 携带结构化 Track 地址。修改 Companion 代码后
重新构建项目 package。

## 5. 迁移 Model 与 Provider 包

Model package 拥有完整 request Type、精确 Capability、result Type、默认值与限制。Generation
不规定通用 text/media/scalar 端口本体或跨模型来源限制。直接 contract 使用
`defineModelModule()`；可选字段式 helper 只是实现选择，不是协议。

Provider 单向依赖它实现的精确 Capability。Endpoint 只有一份权威 `capabilities` 列表。只有
Producer 产生 Need 后，请求支持、调度和实时定价才接收具体请求。Immediate handler 与异步完成
结果都直接返回递归 `Value`。

## 6. 迁移 Frontend 与执行集成

Source frontend 从 `decode()` 直接返回当前文档，并使用 `@hypit/source` 的 `SourceUnit`。
Target 是公共 Output 名称，用字符串表示。

框架集成使用以下边界：

- `AuthorGraph` 包含具有固定 Operation result 的作者 Output 与 Operation。
- 面向作者的 Target 集合解析为 `{ name, output, type }` 条目，选择一次有限执行。
- `BuildCompiler` 把显式 Source 与 Target 参数送入同一 Author 编译；不再有独立的 Invocation
  package、preset 文档或 compiler。
- Kernel 持久化不可变 `BuildDefinition` 与有序 `BuildFact[]`；`BuildView` 是派生读取视图。
- 编译后的 Target 独立记录本次要求的执行目标，不承担存储语义。
- `ResultIntent` 只命名可达的 package-owned retained Output 及其最终 Record。
- Result 保存自包含的当前值与文件，不转发到其他 Build。
- open Result draft 是 Repository 的可写状态，不是历史 `BuildResult`。只有 finished Result
  才有 outcome、完成时间、execution log 与外部 operation evidence。
- Result 不保存可编辑或提交时固定的 title。Source、Target、Build id 与 retained Output 构成
  记录身份；主观命名应留在作者项目材料中。
- Result operation evidence 只保留 Provider 确认/完成事实、回执与明确结论。Runtime id、排队阶段、
  progress、capacity pool 和未获确认的 queued work 不进入历史。
- `hypit result export <build-id> --output <name> --to <path>` 写出一个留存 Output；结构化 Type
  使用其所属 package 提供的作者格式导出器。

Result Manifest 使用 `sourcePath` 记录 Author Source 路径。plan JSON 投影 Target、外部请求与诊断，
不序列化 Producer 的 Step/Port/Record 连接。当前数据库与 Result 读写方应共同更新，不增加字段
别名或按形状猜测。

## 7. 验证迁移后的作品

运行拥有改动边界的框架与 package 检查，然后验证真实项目：

```sh
hypit check main.svml
hypit plan main.svml --target final.video
hypit studio --source main.svml --target final.video
```

检查生成媒体选择、Timeline extent、视觉顺序、音频、Caption timing 和最终渲染。项目与 lockfile
已全部迁移到当前接口后，删除迁移专用
脚本。
